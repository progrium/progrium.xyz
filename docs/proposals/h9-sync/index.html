h9 proposal: sync client and server

Summary

h9 gains two modes that together give wanix general-purpose synced storage: a server mode that holds user roots and orders every change, and a sync client mode that keeps a local, offline-capable copy of a root and serves it over 9P. Both speak 9P2000.L over a WebSocket and share one small file interface under .fs/.

Motivation

  • wanix needs mutable user storage (home folders and user data) that works the same from the browser, from native h9, and eventually from native apps.
  • Syncthing gives the right user expectations (local copies, offline edits, and visible conflict copies) but needs full copies on every node, peer-to-peer networking, and no browser path.
  • A star topology with the server as the single ordering point makes sync simpler than Syncthing's (one version number per file instead of version vectors) and faster to converge (changes are pushed to every client in one round trip).

Scope

  • In scope: the .fs interface, versioning and conflicts, h9 server mode, and h9 sync client mode, including the browser.
  • Deferred: OS integration (native on-demand files on Linux, macOS, and Windows). This proposal only defines the boundary h9 exposes to it.
  • Out of scope: version history and archiving, peer-to-peer sync, sharing a root between users, and the storage backend under the server's files.
  • This is separate from the mount-index proposal and does not change it. If it proves out, the .fs index could later replace /.h9index.

Overview

One h9 binary runs in either mode, and every device talks only to the server.

| | Server mode | Sync client mode | | --- | --- | --- | | Runs on | an internet-reachable host | each native device, and in the browser | | Holds | every user root as plain files, plus SQLite metadata and the change log | one or more roots: a mirrored index, hydrated content, and a queue of local changes | | Serves | 9P2000.L over WebSocket at /9p, with .fs/ in each root | the synced root inside h9's namespace, and over 9P on a local socket for OS integration | | Talks to | clients | the server, over 9P2000.L over WebSocket |

Transport and auth

  • The client opens a WebSocket to /9p and authenticates on the HTTP upgrade with a cookie or bearer token. 9P's Tauth is unused.
  • Tattach with aname set to the root (home/jeff). The server checks that the authenticated user owns it.
  • 9P is tagged, so many requests are in flight at once on one connection. A client may open a second connection for bulk transfer so a large upload doesn't stall small reads.
  • Raw 9P over TCP or a Unix socket works the same, for local and testing use.

Plain clients still work

A 9P client that knows nothing about .fs/ (a shell over a mount, or h9 attaching directly without sync) can read and write normally. Plain writes apply as last-writer-wins when the fid is clunked and still produce events, so sync clients see them.

The .fs interface

Each root (and each directory with its own index) has four synthetic entries under .fs/: index, events, ctl, and stage/. The index and the event stream are one log seen two ways, so a client bootstraps from the snapshot and then tails changes.

.fs/index

A snapshot of the whole tree at one sequence number. The header line is always plain text:

fsindex 1 seq <N> [<encoding>]

Then one line per path, sorted by path in byte order:

fsindex 1 seq 48211
/ d 0755 0 1763491200 48000 - -
/.config d 0755 0 1763491100 47950 - p
/.config/git/config f 0644 212 1763400000 31002 b3:5e1a… p
/Documents/Tax%202025.pdf f 0644 284113 1763480011 46990 b3:9f2c… -
/Notes/todo.md f 0644 812 1763491190 48211 b3:11ab… p
/Photos d 0755 0 1763491000 48100 - i

| Field | Meaning | | --- | --- | | path | from the root, percent-escaped for space, %, newline, and non-UTF-8 bytes, so every name is listed | | type | d directory, f file, l symlink (target follows the flags) | | mode | permission bits, octal | | length | bytes; 0 for directories | | mtime | seconds since the epoch | | version | the seq of the path's last change | | hash | BLAKE3 of the content for files, - otherwise | | flags | -, or any of p (prefetch) and i (own index) |

  • Encoding. A client writes accept zstd to the index fid before reading; the server may then end the header with zstd and send the rest as one zstd frame. Without it the body is plain text, so cat .fs/index works.
  • Freshness. qid.vers of .fs/index is its seq, so Tstat tells a client whether a cached copy is current.
  • Nested indexes (i). A directory flagged i has its own <dir>/.fs/index, events, and ctl. The parent lists the directory but none of its children, and versions inside are scoped to it. Use it for very large or busy subtrees, or a mount of another system that serves its own index. Clients fetch it the first time something walks in.
  • Prefetch (p). A file flagged p should be hydrated right after the index is read; on a directory it covers everything under it. It is a root-wide hint, unlike a per-device pin.

.fs/events

A stream of change records. A client may write since <N> before reading; without it, the first record is seq <current> and live changes follow. Each read returns one or more records and blocks when there are none, so a pending Tread is the push channel, and Tflush cancels it.

48212 put /Notes/todo.md f 0644 830 1763491250 48212 b3:77d0… p dev=mac-a1
48213 del /Downloads/old.zip 48213 dev=linux-b2
48214 mv /Draft.md /Posts/Final.md 48214 dev=mac-a1
48215 flags /Projects p 48215 dev=mac-a1
  • put carries the full index line for the path; del and mv carry the new version; flags changes only the flags.
  • If N is older than the retained log, the read fails with Ereset and the client re-reads the index.
  • Two ways to bootstrap without a gap: read the index at N and then since N, or open events first, read the index at some M, and drop records at or below M.

.fs/ctl

One command per Twrite; the reply is read back from the same fid.

| Command | Effect | Reply | | --- | --- | --- | | hello <device-id> | names this client for events and conflict copies | ok | | commit <stage> <path> <base> <mtime> <mode> | publishes a staged file if the path is still at base | ok <version> or conflict <version> | | commit-hash <hash> <path> <base> <mtime> <mode> | the same, using content the server already holds, so no upload | ok <version>, conflict <version>, or missing | | mkdir <path> <base> | creates a directory | ok or conflict | | rm <path> <base> | deletes a file or an empty directory | ok or conflict | | mv <from> <to> <base> | renames, keeping content | ok or conflict | | prefetch <path> on\|off | sets or clears p | ok <version> |

.fs/stage/

A client creates a file here and writes bytes at any offset, so an interrupted upload resumes where it stopped. Nothing is visible in the tree until commit. Unused stage files expire after a day.

Versions, commits, and conflicts

Because the server orders every change, a file's version is the seq of its last change, and conflict detection is a compare-and-swap against the version a client started from.

Versions

  • Each root (or nested index) has a seq that increases by one on every change: put, delete, mkdir, move, or flag change.
  • A deleted path keeps a tombstone with its delete seq until the log is compacted.
  • 9P qid.vers carries the low 32 bits of the version; the index and events carry it in full.

Commit

  • If the server's current version for the path equals base (0 for a new path), the server applies the change, assigns the next seq, emits the event, and replies ok.
  • Otherwise it replies conflict <version> and changes nothing.
  • The reply and the event travel on the same connection in order, so a client never races its own change.

Conflict resolution (Syncthing behavior)

  1. The server's copy stays at the path, and the client fetches it.
  2. The client renames its own copy to name.sync-conflict-<YYYYMMDD-HHMMSS>-<device>.ext and commits that as a new file.
  3. Every client then sees both files.

The first commit to reach the server wins, rather than Syncthing's newer-mtime rule. That is deterministic, and the other side's work is never lost.

Deletes and renames

  • rm with a stale base is a conflict: the edit wins and the file stays, as in Syncthing.
  • mv is atomic on the server and keeps the hash, so other clients rename locally without downloading. A stale base on the source falls back to copy plus delete.
  • Deleting a directory with changes the client hasn't seen fails; the client removes what it saw and leaves the rest.

Sync client mode

In sync client mode h9 mirrors a root's index locally, hydrates file contents on demand, and queues local edits, so the root stays fully usable while the server is unreachable.

Local store

One cache folder per device (per origin in the browser), holding:

  • state.db (SQLite): the mirrored index, the last seq applied per index, the device id, and per-path state and base version.
  • content/<hash>: hydrated bytes keyed by content hash. Identical files are stored once, and a file whose hash is already present hydrates with no download, so renames and copies are free.
  • work/: private copies of files being written. Shared content is never edited in place; a write copies to work/, and the result is re-keyed by hash when it commits.

Each path is in one of four states: placeholder, hydrated, dirty, or pinned (a device-local override that keeps it hydrated).

A dirty file is never evicted, and a conflict leaves the server's copy at the path while the local edit lives on as a separate conflict file.

Bootstrap

  1. hello <device-id>, then read .fs/index with accept zstd.
  2. Write the index to state.db; every file starts as a placeholder.
  3. Collect p files whose hash isn't in content/ and fetch them, many reads pipelined on one connection.
  4. Open .fs/events with since <N> and start the events loop.

After bootstrap, a reconnect resumes from the stored seq and never rereads the index unless it gets Ereset.

Events loop

  • put with a new hash: update the entry; a hydrated copy becomes stale and is refetched if pinned or prefetched, or dropped back to placeholder otherwise.
  • mv: rename locally and keep the content.
  • del: remove the entry; a dirty local copy turns into a conflict copy instead.
  • Every applied change is passed on as an invalidation to whatever has the root mounted (h9's namespace, or OS integration later).
  • Events for this device's own commits are recognized by seq and only advance the stored seq.

Reads and writes

  • A read of a placeholder walks, opens, and reads the server file; concurrent reads of the same file share one fetch.
  • A write marks the path dirty and records the base version it started from. On close the client stages and commits; for content the server may already have, it tries commit-hash first.
  • A conflict reply triggers the resolution in the previous section.

Offline

  • Hydrated and pinned files stay readable and writable. A placeholder that was never hydrated returns an offline error rather than blocking.
  • Local changes queue in state.db with their base versions and drain in order on reconnect, through the same commit path.

Eviction

An LRU over hydrated files that are in sync and neither pinned nor prefetched, with high and low watermarks on the cache size. Dirty files are never evicted. In the browser the budget comes from navigator.storage.estimate(), and the client asks for persistent storage so the browser doesn't clear it.

Server mode

In server mode h9 keeps each root as plain files at their real paths and puts all metadata and the change log in SQLite, so the store stays browsable and backups are ordinary file copies.

Storage

  • roots/<root>/...: file bytes at their real paths.
  • stage/: uploads in progress, on the same filesystem as roots/ so commits are renames.
  • meta.db (SQLite), per root: the current seq, one row per path (type, mode, length, mtime, version, hash, and flags), and the change log.
  • The index snapshot is generated from the path table and cached per seq and encoding, so repeated bootstraps are cheap.
  • Whatever sits under roots/ (local disk, ZeroFS, or anything else) is outside this proposal.

Write path

  1. A client writes bytes into a stage file.
  2. On commit, the server hashes and fsyncs the stage file, then in one SQLite transaction checks the base version, bumps the seq, updates the path row, and appends to the log.
  3. It renames the stage file into place and wakes every pending events read on that root.
  4. On startup it repairs any log entry whose rename didn't happen before serving.

Auth

  • Token or cookie on the WebSocket upgrade; the server maps it to a user.
  • A root belongs to one user. Tattach to someone else's root fails.
  • Sharing, quotas, and per-file permissions are out of scope for now.

Log retention

The log keeps a fixed window (for example 30 days or 1 million entries). Tombstones older than the window are dropped, and a client behind the window gets Ereset and rereads the index. The window only affects how often a long-offline client pays for a full index read, never correctness.

External writers

If something else writes under roots/ (for example a keepsync node restoring from its archive), the server notices it through a file watcher plus a periodic rescan and turns each change into an ordinary commit and event. Read-only tools such as an archiver need nothing extra.

Boundary with OS integration

Native on-demand files on Linux, macOS, and Windows are deferred, but h9 should expose one contract now so that layer can stay thin and avoid storing files twice.

h9 serves the synced root over 9P on a local socket and adds a few local-only extensions an OS driver can use:

  • Metadata from the mirrored index, so listing and stat never wait on the network.
  • Invalidations as a local .fs/events stream, forwarded from the events loop.
  • Backing files. For a hydrated file, h9 can return the path of its file in content/ (or work/ while dirty), so a driver can let the kernel read it directly: FUSE passthrough on Linux, or APFS clones on macOS. No second copy is kept.
  • Hydrate on request. Opening a placeholder through the local endpoint hydrates it first, so a driver never needs to talk to the server.
  • Writes from the driver are plain 9P writes to h9, which handles base versions and conflicts upstream.

Which driver each platform uses (FUSE, FSKit or File Provider, and ProjFS or cfapi) is the follow-up proposal.

Prior art

No existing system matches this design exactly, but each piece has a close precedent. Coda is the nearest overall, and Dropbox's API is the nearest in wire shape.

| System | What it is | What we borrow | How we differ | | --- | --- | --- | --- | | Coda (CMU, from AFS) | distributed filesystem with whole-file caching, server callbacks, and disconnected operation | the client modification log (our dirty queue) and replay with conflict detection on reconnect | one version per file instead of per-volume version vectors; 9P instead of a kernel module | | Plan 9 replica(1) | tools that sync a tree from a database of paths plus a change log | the index plus log model | a live stream (.fs/events) instead of batch applylog runs | | Upspin | global namespace with separate directory and storage servers | Watch(name, sequence), which streams changes after a sequence number | files on the server, not content in separate stores; one ordering server per root | | Dropbox API v2 | HTTP sync API | list_folder snapshot plus cursor, continue for deltas, and longpoll to block; hash dedupe and resumable uploads | 9P instead of JSON over HTTP; the blocking read is the push channel | | Google Drive changes, OneDrive delta | HTTP change feeds | the same snapshot and change-token shape | the same differences as Dropbox | | WebDAV sync-collection (RFC 6578), Nextcloud | sync-token deltas, with If-Match and ETags for writes | compare-and-swap commit against a version | a single push stream instead of polling PROPFIND | | Syncthing BEP | peer-to-peer block exchange protocol | Index and IndexUpdate keyed by sequence; conflict-copy naming | star topology; a server-assigned version instead of version vectors | | EdenFS (Meta), VFS for Git | lazy hydrate-on-read checkouts of huge repos | per-platform drivers (FUSE, ProjFS, loopback NFS on macOS) | reference for the deferred OS integration proposal |

These descriptions are from memory; links and a check against each system's documentation are still to add.

Relation to mount-index

The .fs/index format is a deliberate iteration on /.h9index, but this proposal leaves the mount-index proposal unchanged until sync is proven. The differences, if it is later folded in:

| | /.h9index today | .fs/index | | --- | --- | --- | | Names with spaces or non-UTF-8 | left out, directory marked !unindexed | percent-escaped, always listed | | qid.vers | 0, trees never change | the path's version | | Changes | regenerate the whole file | .fs/events stream with tombstones | | Content identity | none | BLAKE3 hash per file | | Hints | none | p prefetch, i nested index | | Encoding | plain text | plain, or zstd after an opt-in |

Milestones

  1. Server mode: 9P over WebSocket, .fs/index, .fs/events, .fs/ctl, staging, and commit, with token auth.
  2. Sync client mode: local store, bootstrap, hydration, the events loop, and commits, served in h9's namespace. Two clients on one root prove conflicts, offline edits, and reconnect.
  3. Browser: the same client against browser storage.
  4. Measure: time to bootstrap and list a 100k-file root, first-byte latency on hydration, and convergence time between two clients, against Syncthing on the same data.
  5. Local endpoint: the boundary contract above, ready for the OS integration proposal.
